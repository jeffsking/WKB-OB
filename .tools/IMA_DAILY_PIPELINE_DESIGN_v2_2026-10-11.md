### 0.1 关键结论：现有脚本解决不了"新增发现问题"

`.tools/ima_note_backfill.py` 的 `collect()` 是**从本地 `RAW/` 向上遍历**，找"RAW 侧是占位符、RAW_FULL 侧没正文"的缺口。

> **它只能修「已落盘但没正文」的条目，永远看不见「IMA 里有、vault 里根本没有」的条目。**

这就是当前自动化体系的唯一结构性缺口：**没有 discovery（发现）环节，只有 repair（修复）环节。**

### 0.2 判重的法定入口（v2 新增）

**一切"是否已编译"的判定，必须走 `.tools/wkb_dedup.py`，禁止手写脚本另算。**

```bash
python .tools/wkb_dedup.py scan               # 全库对账（先自证覆盖率再给结论）
python .tools/wkb_dedup.py scan --out x.json  # 落盘清单
python .tools/wkb_dedup.py check <RAW相对路径> # 判定单条
```

工具**强制**先输出自证（页面总数 / 含登记页数 / 登记路径数 / 单值页数 / 多值页数），匹配为 0 时 `sys.exit(1)` 拒绝出结论。

**原因**（AGENTS.md §1.1.2 三条铁律，均为当日实证教训）：

1. 正则禁用 `\s*`，一律 `[ \t]*` —— `\s*` 贪婪吞换行会让全库已登记路径**一条都匹配不到**
2. 扫描后**必须先自证覆盖率** —— 否则文件名缺 `.md` 后缀会静默全跳过，得出**假的「零重复」**
3. 跨文件判重**必须用 difflib** —— `US9162007` 两份 sha1 不同但相似度 **0.9996**，`sha1 不同 ≠ 内容不同`

## 3. 判重与状态机制（本方案的核心）

### 3.1 三级判重键

| 级别     | 键                     | 作用                 | 防的是         |
| ------ | --------------------- | ------------------ | ----------- |
| **主键** | `media_id`            | 唯一身份，跨路径跨改名恒定      | 同一条目被重复入库   |
| **次键** | `kb_path`（文件夹链 + 文件名） | ledger 丢失后可从本地反查恢复 | 账本损坏导致的漏判   |
| **指纹** | 正文 sha1 / difflib 相似度 | 同物改名 / 异名同物        | 标题变更导致的重复编译 |

> **为什么不能用"路径 + 文件名"当唯一键**：实测本地有 **11 组同名文件分布在不同路径**。它们是不同条目，不是重复。**必须以 `media_id` 为准。**

### 3.2 五态状态机（**同步层**，与编译层 `knowledge_update_status` 正交）

| 状态              | 含义                  | 进入条件                                       | 下一步        |
| --------------- | ------------------- | ------------------------------------------ | ---------- |
| `discovered`    | 已枚举到，本地无正文          | ledger 无记录                                 | 进 B        |
| `synced`        | `RAW_FULL` 已有正文     | `extract_status: ok\|empty\|original-only` | 进 C        |
| `compiled`      | WIKI 源摘要页已建且 `done` | source 页存在                                 | 终态         |
| `manual_review` | 敏感 / 冲突 / 无法处理      | 命中 §5 边界                                   | 等人工        |
| `absent`        | IMA 侧已删除            | 枚举时本地有、IMA 无                               | 记档**不删本地** |

### 3.3 移动检测

```
枚举得 media_id + 当前 kb_path
        ↓
   ledger 命中？
   ├── 否 → 新增 → discovered
   └── 是 → 比对 kb_path
            ├── 相同 → 已处理，跳过
            └── 不同 → **移动**
                 ├─ 记 moves[]: {from, to, date}
                 ├─ 更新 kb_path（账本跟随）
                 ├─ 编译层：更新 source 页 source_path（元数据修正，记 log）
                 └─ **不移动本地文件**（保 RAW ↔ RAW_FULL 1:1 镜像不破）
                    提供 `--apply-moves` 开关，人工决定是否真搬
```

**为什么默认不搬文件**：`RAW/` 是插件维护的只读层（AGENTS.md §0 红线），AI 搬 `RAW_FULL` 会立刻破坏 1:1 镜像，插件下轮同步又会按旧路径重新生成，陷入拉锯。**记映射、不搬文件**是唯一稳定解。

### 3.5 merged 页识别规则（**v2 新增，必读**）

**背景**：09-30 治理时把重复页转为 `status: merged` 的指针页，但**刻意保留原 `source_path`** 作合并存档线索（治理脚本 `_merge_dupes_governance_20260930.py` 对 `source_path` 的 grep = 0 次）。后果：**这些页必然呈现"一条 RAW 被 2 页登记"，且每次扫描都会重现为告警。**

**枚举器/编译器的正确处理**：

| 页面状态             | 在 `wkb_dedup.py` 中的处理 | 在本管道中的处理          |
| ---------------- | --------------------- | ----------------- |
| `status: merged` | **留在已编译索引内**（防误报未编译）  | 视为**已编译**，不进入阶段 C |
| `status: merged` | **从重复登记告警中剔除**        | 不报为"重复编译"         |

当前全库：`status: merged` 页 **21** 个，其中仍持 RAW 侧 `source_path` 的 **4** 个（2 条触发登记 + 2 条独享路径）。

**教训**：只看「多页登记 RAW」而不看页面状态，会得出「重复永远治不完」的假象。

### 3.6 两个账本的正交关系（v2 新增，防混淆）

| 账本        | 文件                             | 管什么                                | 谁维护           |
| --------- | ------------------------------ | ---------------------------------- | ------------- |
| **同步层账本** | `.tools/_ima_sync_state.json`  | IMA 条目 ↔ 本地落盘（discovered/synced/…） | 本管道阶段 A/B     |
| **编译层判定** | `wkb_dedup.py scan`（无独立文件，实时算） | RAW ↔ WIKI source 页（已编译/未编译）       | 阶段 C 前后各跑一次对账 |

**铁律**：同步层账本**不得**作为"是否已编译"的判据；反之亦然。两者交集在 `media_id ↔ source_path` 映射。

#### 3.6.1 `source_page_hint` 缓存字段（**v2 定案，王总 2026-10-11 裁定**）

**决定**：同步层账本**冗余存**编译线索，但**明确降格为"缓存提示"而非权威数据**。

```json
{
  "_warning": "source_page_hint 仅为加速排查的缓存线索，非权威。判定『是否已编译』一律以 wkb_dedup.py scan 为准。",
  "items": {
    "note_3867e2b6...": {
      "stage": "synced",
      "source_page_hint": "WIKI/sources/会议纪要：OI 十月供应商考察.md"
    }
  }
}
```

**为什么需要**：`wkb_dedup.py scan` 每次要遍历全库 1675 个页面现场计算，**不能随手翻一眼就知道**某条编没编。存一份 hint 可让排查单条时秒查。

**风险与对冲**：

| 风险                                                           | 对冲措施                                                                  |
| ------------------------------------------------------------ | --------------------------------------------------------------------- |
| hint 会过期（WIKI 侧手工合并页面、改路径后账本不跟随）→ **账本成了错误信息源**（与当日"假欠账"同款病） | **一致性校验**：`wkb_dedup.py scan` 每次跑完顺手比对账本 hint，不一致则**打标记提示（只提示、不自动改）** |

**命名铁律**：字段名必须是 `source_page_hint`（**不能叫 `source_page`**）——防止后来者误当权威字段引用。

**校验实现**（阶段 C 集成）：

```
wkb_dedup.py scan 完成
    ↓
读取 _ima_sync_state.json 的 source_page_hint 列
    ↓
逐条比对扫描结果的"已编译"集合
    ├── 一致 → 无输出
    └── 不一致 → 输出 [hint 过期] 清单：media_id / hint 值 / 实际值
               （仅提示，由人工跑 `baseline` 刷新，工具不自动改）
```

## 4. 枚举器设计（阶段 A）——含成本控制

### 4.1 全量递归的真实成本

247 个文件夹 + 1378 条目，按 MCP `limit ≤ 50` 分页：

```
约 245 次目录调用 + 约 28 次翻页 ≈ 273 次 MCP 调用 / 全量扫描
```

每日全量不现实。**剪枝策略**：

### 4.2 `file_number` 变化检测（关键优化）

MCP 返回的文件夹对象自带 `folder_info.file_number`（直属文件数）与 `folder_number`（子文件夹数）——**免费的廉价变更信号**。

```
枚举根层 → 拿到 5 个顶层文件夹
    ↓
逐个比对账本里的 file_number + folder_number
    ├── 与上次一致 → **不进入该目录**（省下一次调用）
    └── 有变化 → 进入枚举，并更新账本
    ↓
对进入的目录，只取 create_time ≥ 水位 的条目；更早的只核对存在性
```

**典型日增量**：5 次根层 + 少数变动目录 ≈ **8~15 次调用**（vs 全量 273）。  
**兜底**：每周一次强制全量递归对账，防止剪枝漏判。

### 4.3 只取已解析完成的条目

枚举时带 `filters: [{filter_type: MEDIA_TYPE_FILTER_TYPE, media_state_filter: {media_states: [MEDIA_PARSE_SUCCESS]}}]`，跳过 `MEDIA_PARSING` 的半成品，避免拉到空壳。

## 5. 落地器设计（阶段 B）——通道分级沿用已验证结论

| 通道    | 手段                                   | 配额               | 适用                                                     |
| ----- | ------------------------------------ | ---------------- | ------------------------------------------------------ |
| **A** | MCP `fetch_media_content`            | **无日配额**         | 笔记 / 录音 / session / 网页（`media_type ∈ {11,12,15,20,2}`） |
| **B** | REST `get_media_info` → 签名 URL → GET | 宽松               | 无文字层原件（图纸图片 / 扫描件 PDF / Office / CSV），**含录音音频**        |
| **C** | REST `get_doc_content`               | **受日配额（200005）** | 仅兜底，命中即当日放弃，**禁止循环重试**                                 |

#### 5.1 录音（media_type=15）双落盘策略（**v2 定案，王总 2026-10-11 裁定**）

录音**同时落转写文本 + 音频原件**，但设**大小阈值**防仓库膨胀：

| 原件大小        | 处置                                                                                |
| ----------- | --------------------------------------------------------------------------------- |
| **< 50 MB** | 转写文本 → `RAW_FULL/<条目目录>/<标题>.md` 正文；音频原件 → `RAW_FULL/<条目目录>/attachments/<原始文件名>`  |
| **≥ 50 MB** | 只落转写文本；音频原件**不下载**，仅在正文 front matter 记 `original_media_id` + 尺寸，供需要时按 §5 通道 B 单独取 |

**理由**：20 MB 级音频单条可接受，但若日后出现长会议录音（1-2 小时），无条件全落会让 RAW_FULL 迅速膨胀到 GB 级，且音频无检索价值——**转写文本才是知识载体，原件只是溯源凭证**。

**阈值可调**：`.tools/` 内配置常量 `AUDIO_ORIGINAL_MAX_MB = 50`，按实际情况调整。

**落盘铁律**：

1. 正文一律写 `RAW_FULL/<同相对路径>`，**绝不写 `RAW/`**（只读红线）
2. 原件落 `RAW_FULL/<条目目录>/attachments/<原始文件名>`，用回原名
3. 原件扩展名按 **Content-Type → 魔数 → 前缀** 三级判定
4. `extract_status ∈ {ok, empty, original-only}` 即视为终态，**不再重跑**
